# Larpsec — интерфейс анализа документов

Интерфейс на React и TypeScript подключён к серверному API `/api/v1`. Он работает с
комплектами документов до/после, состоянием анализа, результатами и исходными цитатами.
Данные сравнений и оригиналы сохраняет бэкенд; после обновления страницы интерфейс
восстанавливает текущее сравнение по сохранённому в браузере идентификатору.

## Запуск всего приложения

Из корня репозитория:

```bash
./run.sh
```

Нужны Node.js 22.12+ с npm/npx, Python 3.12–3.14 и uv. Скрипт использует pnpm 10.30.3
из `package.json`, устанавливает зависимости по lock-файлам, собирает `frontend/dist`
и запускает FastAPI. Откройте **http://127.0.0.1:8000**. Глобальная установка pnpm не нужна.
Настройка режима анализа описана в [корневом README](../README.md).

## Разработка интерфейса

В первом терминале из корня репозитория:

```bash
./backend/run.sh
```

Во втором:

```bash
cd frontend
npx --yes pnpm@10.30.3 install --frozen-lockfile
npx --yes pnpm@10.30.3 dev
```

Откройте **http://127.0.0.1:5173**. Vite проксирует `/api` и `/health` на сервер
`http://127.0.0.1:8000`, сохраняя пути. Адрес API по умолчанию — `/api/v1`.
Без работающего бэкенда серверные операции показывают ошибку подключения.

Если нужны другие адреса, создайте локальный `frontend/.env` из `.env.example`:

```dotenv
VITE_API_BASE_URL=/api/v1
API_PROXY_TARGET=http://127.0.0.1:8000
```

`API_PROXY_TARGET` применяется только к dev-серверу Vite. `VITE_API_BASE_URL` попадает
в сборку: после изменения нужна новая сборка и перезапуск сервера. Для абсолютного
адреса API настройте `CORS_ORIGINS` на бэкенде. При запуске через `./run.sh` сайт и API
имеют общий origin, отдельный прокси и CORS для обычного сценария не требуются.

Модельный ключ `LLM_API_KEY` хранится только на сервере. Не помещайте секреты в `VITE_*`:
эти переменные видны посетителям сайта. Если на сервере задан общий `API_TOKEN`,
запросы `/api/v1` требуют `Authorization: Bearer <токен приложения>`.
Введите его на сайте в разделе **«Доступ к серверу»** → **«Токен доступа»** →
**«Сохранить подключение»**. Он сохраняется в sessionStorage текущей вкладки
(`larpsec.apiToken`) и не встраивается в файлы приложения.

## Работа с документами

1. Продолжите текущее сравнение или нажмите «Новое сравнение».
2. Добавьте документы в комплекты «до» и «после»: DOCX, PDF с текстом или XLSX.
3. Проверьте предупреждения извлечения и подтвердите полноту комплектов, если она известна.
4. Запустите анализ и дождитесь завершения; состояние хранится на сервере.
5. Изучите сопоставление подразделений и функций, замечания и цитаты источников.
6. Скачайте заключение в Markdown или структурированный результат JSON.

Для готового сценария нажмите **«Загрузить пример „до/после“»** и **«Запустить сравнение»**.
Это настоящая загрузка пары `public/examples/before.docx` и `after.docx` в текущий бэкенд.
После завершения используйте **«Открыть результаты»**. Для своего файла нажмите
**«Выбрать документ»**, укажите сторону и подтвердите **«Обработать документ»**.

### Текст до / после

После обработки документов обеих версий нажмите **«Сравнить текст»** или откройте
**«Сравнение» → «Текст до / после»**. Выберите файл для каждой колонки: слева отображается
версия «до», справа — «после». Удалённые строки подсвечены красным со знаком минус,
добавленные — зелёным со знаком плюс; изменённая строка показана в обеих колонках.
Можно оставить только изменения и переходить между их блоками.

Этот просмотр доступен до запуска анализа функций и использует уже извлечённый текст.
Форматирование Word не воспроизводится; качество извлечения PDF влияет на подсветку.
Результаты серверного анализа доступны во вкладке **«Анализ функций»**.

Сервер проверяет формат, размер и содержимое каждого файла. До запуска анализа можно
удалять документы из черновика. Запущенный или завершённый комплект зафиксирован;
для других исходных файлов создайте новое сравнение. Источники выводятся текстом,
без исполнения HTML из документов. Шрифты включены в сборку, внешние CDN не требуются.

По умолчанию сервер использует **demo — буквальные правила без ИИ**. Это реальная
обработка загруженных файлов с ограниченными возможностями распознавания, а не обещание
семантического анализа произвольного текста. Для свободных формулировок настройте
`ANALYSIS_MODE=llm`, ключ и модель на бэкенде. Ошибка модели не заменяется demo-результатом.

Учебные документы можно создать из корня репозитория:

```bash
cd backend
uv run --frozen --no-dev python -m scripts.make_demo
```

Загрузите `backend/data/demo/before.docx` и `after.docx` в соответствующие комплекты.
Это синтетические примеры; ожидаемые изменения описаны в [examples/scenario.json](../examples/scenario.json).

## Проверки и сборка

Из каталога `frontend`:

```bash
npx --yes pnpm@10.30.3 build
npx --yes pnpm@10.30.3 test
npx --yes pnpm@10.30.3 exec playwright install chromium firefox
npx --yes pnpm@10.30.3 test:e2e
npx --yes pnpm@10.30.3 test:api
```

`build` проверяет TypeScript и создаёт production-сборку в `dist/`. Для обычного
просмотра этой сборки используйте `../run.sh`: Vite preview сам по себе не предоставляет
серверные операции. Итоги выполненных проверок фиксируются в [docs/VALIDATION.md](../docs/VALIDATION.md).

Основной HTTP-контракт: [docs/API.md](../docs/API.md). Особенности подключения клиента:
[docs/API_CONTRACT.md](docs/API_CONTRACT.md). Машиночитаемая схема: [docs/openapi.json](../docs/openapi.json).

## Ограничения

OCR, бинарные DOC/XLS и интерпретация изображений не поддерживаются. PDF с изображениями,
формулы Excel и другие ограничения извлечения снижают подтверждённое покрытие анализа.
Цитаты проверяются на наличие в документах; смысл выводов требует проверки сотрудником.
Сервис предназначен для одной доверенной команды, без отдельных пользовательских аккаунтов.
