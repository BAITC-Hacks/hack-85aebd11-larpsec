# Larpsec — фронтенд

Первый этап сервиса: загрузка **DOCX**, извлечение и просмотр текста. Интерфейс на русском, адаптирован для компьютера и телефона.

## Запуск

Требуются Node.js 22.12+ и pnpm 10.30.3. После клонирования репозитория:

```bash
cd frontend
corepack enable
pnpm install --frozen-lockfile
pnpm dev
```

Откройте **http://localhost:5173** в Firefox или Chromium. Если Corepack отсутствует, установите pnpm: `npm install -g pnpm@10.30.3`.

```bash
pnpm build       # TypeScript + production-сборка в dist/
pnpm preview     # Просмотр production-сборки
pnpm test        # Проверка DOCX и схемы ответа API
pnpm exec playwright install chromium firefox
pnpm test:e2e    # Браузерные проверки: Chromium, Firefox, мобильный размер
pnpm test:api    # Проверка интеграции с имитируемыми ответами сервера
```

## Два режима

**Локальный просмотр (по умолчанию).** DOCX действительно читается в браузере библиотекой Mammoth в Web Worker. Файл и текст не отправляются на сервер. Можно искать фрагменты, просматривать нумерованные пункты и скачивать извлечённый TXT. Это извлечение текста, не ИИ-анализ. Шрифты поставляются вместе с приложением, внешних CDN нет.

**Серверный режим.** Создайте `frontend/.env` на основе `.env.example`:

```dotenv
VITE_API_BASE_URL=/api
API_PROXY_TARGET=http://127.0.0.1:8000
```

Перезапустите Vite. POST `/api/documents` будет проксироваться в `http://127.0.0.1:8000/api/documents` **без изменения пути**. Можно указать абсолютный `VITE_API_BASE_URL`, если на сервере настроен CORS. API-ключи и другие секреты нельзя помещать в `VITE_*`: эти значения доступны браузеру.

В production переменные `VITE_*` задаются при сборке. `/api` должен проксировать веб-сервер, обслуживающий `dist/`; dev-прокси Vite там не работает.

Предлагаемый контракт находится в [docs/API_CONTRACT.md](docs/API_CONTRACT.md). Его ещё требуется согласовать с серверным агентом. При ошибке API приложение показывает ошибку; автоматического перехода на демонстрационные данные нет.

## Демонстрация

1. Нажмите «Сначала посмотреть пример» — откроется настоящий учебный DOCX из `public/examples/audit-example.docx`.
2. Введите `5.5.3` в поиск: появится функция подготовки отчётов директора ДККМ.
3. Скачайте текст или вернитесь к загрузке и добавьте свой DOCX.
4. Попробуйте загрузить PDF, пустой или повреждённый файл — интерфейс объяснит ошибку.

Пример явно обозначен как учебный, не является полной редакцией положения и всегда обрабатывается локально, в том числе при включённом API. Для воспроизводимого обновления примера: `python3 scripts/generate-example.py` (Python нужен только для генерации, файл уже включён в репозиторий).

## Что реализовано

- Выбор файла и drag-and-drop, одна загрузка за раз, до 20 МБ.
- Метки «до изменений» / «после изменений».
- Проверка расширения, пустого файла, размера и ZIP-сигнатуры DOCX. Полную проверку содержимого обеспечивает парсер; в серверном режиме её должен повторять сервер.
- Состояния выбора, отправки, обработки, результата и ошибки; отмена и повторная попытка.
- Фактический прогресс HTTP-загрузки; неопределённый индикатор во время обработки, без выдуманного процента.
- Просмотр исходного текста, поиск, фильтр нумерованных пунктов, выгрузка TXT.
- Список документов текущей сессии, фильтры, удаление из сессии, адаптивная вёрстка.
- Доступные с клавиатуры элементы, модальное руководство, сообщения об ошибках.

## Ограничения первого этапа

- Список документов и файлы хранятся **только в памяти** и теряются при обновлении страницы. Удаление из списка не удаляет документ на сервере.
- Только `.docx`. `.doc`, PDF, Excel, OCR, парольная защита и восстановление повреждённых файлов не поддерживаются.
- Просмотр показывает текст; изображения, оформление и исходная сетка таблиц не сохраняются. Номера фрагментов не являются номерами страниц. Вкладка «Пункты» выделяет нумерацию из текста; это не семантический анализ.
- Для защиты отзывчивости интерфейса локальный парсер работает в отдельном Worker с ограничением 25 секунд и результатом до 2 млн символов. Проверки браузера не заменяют серверные ограничения размера распакованного архива.
- API-загрузка имеет таймаут 60 секунд, вся операция — 120 секунд. «Отмена» прекращает ожидание в браузере, но не гарантирует остановку серверной задачи. Повтор после сетевого сбоя может создать ещё одну серверную задачу.
- Сравнение функций, конфликты интересов и аналитические заключения относятся к следующему этапу; пункты навигации пока отключены.
- Реальный сервер партнёра пока не подключён. Контракт проверяется автоматическими тестами с имитируемыми ответами, что не заменяет совместную интеграционную проверку.

## Архитектура и совместная работа

```text
src/App.tsx                 экраны загрузки, списка и результата
src/useDocuments.ts         состояние документов и отмена операций
src/lib/api.ts              адаптер API, валидация ответа, polling
src/lib/local-reader.ts     запуск и завершение Worker
src/lib/docx.worker.ts      извлечение текста из DOCX
src/lib/documents.ts        валидация, нумерация, экспорт TXT
src/lib/types.ts            типы интерфейса
src/styles.css             адаптивное оформление
tests/                     проверки обработки и браузерных сценариев
```

Вся наша реализация расположена в `frontend/`. Корневые файлы и серверная часть не изменены. Серверному агенту достаточно согласовать `docs/API_CONTRACT.md`; изменения формата изолируются в `src/lib/api.ts`.

Технологии: React, TypeScript, Vite, Mammoth, Lucide, Vitest, Playwright. Зависимости зафиксированы `pnpm-lock.yaml`. Для требований среды см. [документацию Vite](https://vite.dev/guide/); API извлечения текста описан в [документации Mammoth](https://github.com/mwilliamson/mammoth.js#extractrawtextinput).
