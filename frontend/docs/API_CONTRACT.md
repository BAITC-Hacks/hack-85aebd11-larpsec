# Предлагаемый контракт DOCX API — версия 0.1

**Статус: предложение фронтенда, требуется согласование с партнёром.** Это описание клиентских ожиданий, не реализация сервера. Серверную часть создаёт второй агент.

## 1. Загрузка

`POST {VITE_API_BASE_URL}/documents`

`Content-Type: multipart/form-data` с boundary, который выставляет браузер. Клиент не задаёт этот заголовок вручную.

| Поле | Значение |
| --- | --- |
| `file` | Бинарный файл DOCX, максимум 20 MiB на клиенте |
| `phase` | `before` или `after` |

Ответ 201 при готовом результате или 202 при асинхронной обработке:

```json
{ "id": "doc-123", "status": "queued" }
```

Допустимые статусы: `queued`, `processing`, `ready`, `failed`.

## 2. Ожидание результата

`GET {VITE_API_BASE_URL}/documents/{id}`

Клиент опрашивает сервер раз в 1,5 секунды, пока статус `queued` или `processing`. Полный таймаут клиентского ожидания — 120 секунд, включая загрузку. Рекомендуется не кэшировать этот endpoint.

```json
{
  "id": "doc-123",
  "status": "ready",
  "result": {
    "text": "5.5.3. Готовит отчеты об итогах выполнения плана работы БВА в соответствии с требованиями настоящего Положения.",
    "paragraphs": [
      {
        "id": "paragraph-42",
        "section": "5.5.3",
        "text": "5.5.3. Готовит отчеты об итогах выполнения плана работы БВА в соответствии с требованиями настоящего Положения."
      }
    ],
    "warnings": []
  }
}
```

- `id` — непустая строка, постоянная для задачи.
- `result.text` — обязательный непустой исходный текст, до 2 млн символов для просмотра.
- `result.paragraphs` — опциональный массив. Если отсутствует, клиент делит текст по пустым строкам. Для точных ссылок будущего анализа рекомендуется возвращать стабильные серверные идентификаторы.
- `paragraphs[].id` — уникальная непустая строка в пределах документа; `text` — строка; `section` — опциональная строка.
- `result.warnings` — опциональные предупреждения для пользователя.
- Клиент выводит текст средствами React, не исполняет HTML и скрипты из документов.

Ошибка самой обработки может прийти с HTTP 200:

```json
{
  "id": "doc-123",
  "status": "failed",
  "error": { "code": "INVALID_DOCX", "message": "Не удалось прочитать документ. Сохраните его заново в формате DOCX." }
}
```

`error.message` отображается как обычный текст. Не возвращайте внутренние стеки ошибок и секреты.

## 3. HTTP-ошибки

| Статус | Отображение в интерфейсе |
| --- | --- |
| 401 / 403 | Нет доступа к обработке |
| 413 | Файл превышает серверный лимит |
| 415 / 422 | Неподдерживаемый или некорректный документ |
| 429 | Слишком много запросов |
| 5xx / сетевой сбой | Сервер недоступен, доступна повторная попытка |

Сервер должен самостоятельно проверять формат, размер файла и размер распакованного архива. Клиентская проверка расширения и ZIP-сигнатуры является предварительной.

## 4. Границы текущей интеграции

- Аутентификация ещё не согласована. Клиент не содержит API-ключей и не отправляет кросс-доменные cookies; same-origin запросы используют обычное поведение браузера.
- Отмена клиентом прекращает XHR/fetch и polling. Серверного endpoint отмены пока нет.
- Повторные запросы не имеют ключа идемпотентности — это нужно согласовать до использования с постоянным хранением.
- Удаление из списка происходит только на клиенте; `DELETE` не вызывается.
- Автоматического перехода на локальный режим при сбое сервера нет.
- Разделы результатов ИИ-анализа и источники сравнительных выводов будут согласованы на следующем этапе.

## 5. Совместная проверка

Поднять сервер на порту 8000; запустить фронтенд с `VITE_API_BASE_URL=/api`; загрузить `frontend/public/examples/audit-example.docx`. Проверить POST, промежуточный статус, GET до `ready`, вывод пункта 5.5.3 и ошибки 413/422. Если у сервера уже другой формат, адаптировать только `src/lib/api.ts` и связанные типы.
