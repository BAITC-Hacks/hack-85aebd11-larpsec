# Эталон сравнения положений о внутреннем аудите

Материалы для проверки смыслового анализа на двух предоставленных редакциях положения БВА. Подготовлены параллельно интеграции фронтенда и бэкенда; код приложения и контракт API не изменены.

## Что подготовлено

| Файл | Назначение |
|---|---|
| [changes.md](changes.md) | 41 группа изменений и контрольных сопоставлений: пункты до/после, ожидаемый смысл, недопустимые выводы |
| [false-positive-checks.md](false-positive-checks.md) | 16 проверок против ложных потерь функций, дублирования и конфликтов |
| [reference.json](reference.json) | Те же 41 группа в структурированном виде и 235 подтверждающих цитат с локаторами |
| [verify_reference.py](verify_reference.py) | Локальная проверка контрольных сумм, связей внутри эталона и цитат по исходникам |

**Статус:** эталон составлен и цитаты проверены по источникам. Прогон анализа сервиса по этому эталону **не выполнен**. Число 41 — число сгруппированных случаев, а не число отдельных текстовых правок, функций или ожидаемых находок API.

## Первые случаи для проверки интеграции

1. **RC-04 / FP-01:** в перечне сохранены ДНМ и ДККМ, добавлены ДИТААД и ДОА; ДНМ не «переименован» в ДИТААД.
2. **RC-13 / FP-04:** обязанности по взаимодействию с субъектами СВК перенесены из 5.4.4 в подпункты нового 5.3.3 с изменением ответственных ролей.
3. **RC-19–RC-20 / FP-05–FP-06:** старый 5.5.3 пуст; новый пункт об отчётах соответствует старому 5.5.5. Квартальная и годовая отчётность сохраняется в 5.1.6.
4. **RC-21 / FP-09:** исключение анализа непрерывного аудита из перечня ДККМ не равно потере функции всем БВА и не доказывает новую передачу её другим ролям.
5. **RC-30 / FP-10, FP-12:** права и запреты перенумерованы. Дополнительно **RC-31**: сохранившиеся ссылки в новых 5.10.2/5.10.5 требуют проверки адресатов.
6. **RC-32 / FP-13:** «осуществляется» → «может осуществляться» в 9.15 меняет обязательность конкретного действия.

Затем пройти остальные случаи, включая специальные права без прямого эквивалента, условия независимости и состав отчётности о качестве.

## Как оценивать ответ сервиса

1. Создать сравнение с редакцией 8 на стороне `before`, редакцией 9 на стороне `after`. Проверить исходные файлы и полноту извлечения до смыслового анализа.
2. Сохранить идентификатор сравнения, версию приложения, дату, ответ API/отчёт и подтверждающие фрагменты. Если модель и версия промпта доступны, также записать их.
3. Сопоставить результаты с `cases`: действие, тип нормы, исполнитель, область ответственности, условия, редакция и пункт важнее совпадения слов.
4. Для каждого случая поставить **соответствует**, **ошибка** или **не оценено**. Подтверждать «соответствует» фактическим результатом и источниками. Отсутствие нужного результата или недоступный для проверки этап помечать явно; это не успешный проход.
5. Для 16 проверок FP отдельно убедиться, что в ответе нет недопустимых утверждений. Просто отсутствие находки о потере/дублировании ещё не доказывает правильность извлечения и сопоставления функций.
6. При ошибке записать фактический вывод, ожидаемый вывод и точные пункты. Итог показывать как количество оценённых/неоценённых случаев и ошибок, отдельно по критичным случаям.

Эталон не требует создания находки о риске для каждой редакторской правки или сохранённой функции. Такие случаи можно оценивать по извлечённым сущностям, связям и сопоставлениям, если они доступны. Не нужно искусственно создавать 41 находку.

Шаблон записи результата:

```text
Сравнение / версия / дата:
Случай RC-__ или FP-__:
Статус: соответствует | ошибка | не оценено
Фактический вывод / идентификаторы фрагментов:
Пункты источников:
Обоснование статуса:
```

## Устройство reference.json

- `sources` фиксирует оригинальные файлы, направление сравнения и контрольные суммы.
- `cases` содержит стабильные ID `RC-01`…`RC-41`, категорию, приоритет, ссылки `before`/`after`, `expected` и `forbidden`. `review_required` означает ручную смысловую оценку эталона.
- `evidence` — словарь цитат. Например, `R8:5.5.5` — редакция 8, пункт 5.5.5. Ссылка `R9:5.5.3` ведёт к содержательному преемнику, несмотря на другой номер.
- `absence_checked_in` у случаев исключения обязанности ДККМ перечисляет весь новый блок 5.5. Отсутствие нельзя доказать одной цитатой оставшейся обязанности.
- `locator.kind=pdf_pages` обозначает физические страницы исходного PDF. `docx_body_paragraphs` — все элементы `w:p` внутри `w:body` в `word/document.xml`, включая пустые, в порядке документа. Оба вида локаторов используют счёт с 1 и включают обе границы.
- Цитаты сохраняют исходные слова, пунктуацию и дефисы. Пробельные символы свёрнуты; из PDF удалены отдельные строки с номерами страниц. Ошибки и сомнительные ссылки источника не исправлены.

Это собственный формат эталона, **не JSON запроса/ответа API**. Категории `role_duty_removed`, `reference_quality` и другие не добавляют новые значения в перечисления серверных моделей.

### Сопоставление с текущей моделью бэкенда

| Наблюдение эталона | Как учитывать в оценке |
|---|---|
| Перенумерация с сохранением смысла | Обычно `function_changes.status=preserved`, с проверкой исполнителя и области |
| Прямой перенос части обязанности | `moved`; части старого/нового пункта могут требовать отдельных функций |
| Изменение предмета, условий, обязательности | `modified`, с объяснением конкретного изменения |
| Нет прямого эквивалента специального права | Допустим кандидат `potential_loss` с ограничением предмета и ручной проверкой; не категоричная потеря всей функции |
| Исключение обязанности одной роли при сохранении у других | Учитывать уровень роли; общий вывод о потере функции недопустим, новая передача не всегда доказана |
| Новый департамент в перечне | Допустимо `unit_changes.status=created` в смысле появления в новой редакции; фактическая кадровая процедура не установлена |
| Пустой пункт, сомнительная ссылка, редакторская правка | Замечание к источнику/сопоставлению; не требуется искусственный `finding` о потере или конфликте |

Идентификаторы `fragment_id`, `unit_id`, `function_id` создаются сервисом и могут различаться между запусками. Эталон привязывается к контрольной сумме документа, редакции, пункту и цитате; затем соответствующий фрагмент связывается с ID текущего запуска. Нельзя подставлять `R8:…` вместо реального `fragment_id` в серверные ответы.

Два положения не составляют полный комплект документов организации. Флаги полноты корпуса `before_complete`/`after_complete` не следует выставлять только потому, что успешно загружены оба файла. Полнота извлечения одного положения и полнота описания всех функций организации — разные свойства.

Файл `examples/scenario.json` в проекте содержит отдельный синтетический пример. Его переименования, потери функций и конфликты нельзя выдавать за установленные изменения этих двух положений.

## Повторная проверка цитат

Требуются Python 3 и команда `pdftotext` из Poppler. Из корня репозитория:

```bash
python3 docs/audit-regulations/verify_reference.py --source-dir "/home/issatayyyy/hackalem ai"
```

Скрипт ничего не меняет и не обращается к API. Он проверяет байты исходников, внутренние ссылки эталона и наличие каждой цитаты в указанных страницах/абзацах. Это проверка целостности материалов, а не качества анализа сервиса. При иной версии извлечения PDF возможны различия пробелов внутри слов: сначала сверить исходник и инструмент, а не автоматически переписывать цитаты.

## Границы выводов

Положения позволяют сравнить текст, роли и закрепление обязанностей. Они не подтверждают кадровые перемещения, фактическое исполнение функций или произошедшие конфликты интересов. Для неподтверждённых соответствий и потенциальных потерь сохраняется ручная проверка. Оригиналы документов не исправлялись.
